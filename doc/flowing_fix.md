# Fluid source/flowing fix

## Problem

Fruits Delight currently exposes and uses Registrate's **flowing** fluid entry
(`FluidEntry#get()`) in several places. Some mods expect the **source** fluid entry
(`FluidEntry#getSource()`), so they do not recognize Fruits Delight fluids.

## Registrate facts

`FDFluids` creates fluids through a custom `VirtualFluidBuilder`:

- `src/main/java/dev/xkmc/fruitsdelight/init/registrate/FDFluids.java`
- `src/main/java/dev/xkmc/fruitsdelight/init/entries/VirtualFluidBuilder.java`

Registrate's `FluidBuilder` registers two fluid entries for every fluid:

| Registry ID | Meaning | Accessor |
|---|---|---|
| `fruitsdelight:<name>` | source fluid | `FluidEntry#getSource()` |
| `fruitsdelight:flowing_<name>` | flowing fluid | `FluidEntry#get()` |

The fluid type is registered as `fruitsdelight:<name>` in `ForgeRegistries.FLUID_TYPES`.

`VirtualFluidBuilder` does not change this layout. It only supplies the same custom
`FruitFluid` factory as the source:

```java
this.source(factory);
```

Both the source and flowing entries are therefore `FruitFluid` instances and share
the same `FruitFluidType`.

### `getSource()` is cheap and repeatable

`FluidEntry#getSource()` is just `get().getSource()`. `get()` returns the already-built
fluid object, and `ForgeFlowingFluid#getSource()` returns `properties.getSource().get()`,
a supplier over the pre-built source fluid. There is no allocation, lookup, or
registration work involved.

Calling `getSource()` repeatedly (inside loops, per-recipe, per-render) is harmless.
Cache it in a local only when it makes the code easier to read.

### `FruitFluid` specifics

`src/main/java/dev/xkmc/fruitsdelight/init/entries/FruitFluid.java` overrides:

- `getFlowing()` returns `this`;
- `getSource()` returns the source fluid from `ForgeFlowingFluid.Properties`.

Therefore:

- `convertToStill(source)` -> source;
- `convertToStill(flowing)` -> source;
- `convertToFlowing(source)` -> source;
- `convertToFlowing(flowing)` -> flowing.

The separate `flowing_<name>` entry is not part of the source fluid's flowing state.
It exists because Registrate's `FluidBuilder` always registers it, and because the
source `Properties` references it as the flowing supplier (which `FruitFluid` then
ignores).

## Current call sites using the flowing fluid

### 1.20 branch

  ```java
  }
  ```

- `src/main/java/dev/xkmc/fruitsdelight/compat/create/CreateRecipeGen.java`

  All fluid arguments currently use `.get()`:

  - lines 58, 63, 66, 70, 76, 95, 101, 109
  - lines 154, 159, 167 inside `fluidRecipes(...)`

### 1.21 branch

The same `FDJuice` and `CreateRecipeGen` usages exist, plus:

- `FruitsDelight.java`, `onCauldronRegistration(...)`

  ```java

                 FDFluids.JAM[e.ordinal()].get(), 1000, null);
  ```

## Important nuance about Create

Create already normalizes fluids to their source form in its recipe API:

- `FluidIngredient.fromFluid(...)` calls `fixFlowing()`, which calls
  `FlowingFluid#getSource()`.
- `ProcessingRecipeBuilder.output(Fluid, int)` calls
  `FluidHelper.convertToStill(...)`, which uses `ForgeFlowingFluid#getSource()`
  for Forge flowing fluids.

That is why generated Create recipe JSON already contains IDs such as
`fruitsdelight:apple_jam` even though the Java code passes `.get()`.

This does **not** fix:

- external code calling `FDJuice#getFluid()`;
- 1.21 cauldron fluid registration;
- any other future call site that passes `FluidEntry#get()` to another mod.

Create also compares `FluidStack` fluid identity in `FluidHelper.isSame(...)`, so an
old flowing stack in a tank will not match a source-based ingredient. Existing Create
recipes generated by this mod did contain source IDs, but old stacks produced by other
paths may still be flowing.

Tag-based ingredients solve this without a Mixin: `FluidTagIngredient#testInternal`
checks `stack.getFluid().is(tag)`, so a tag containing both ids accepts both. See
"Old save compatibility" below.

## Recommended fix

### 1. Use the source entry at all fluid call sites

Do **not** change the registration layout in `FDFluids` or `VirtualFluidBuilder`.

Required changes:

- `FDJuice#getFluid()`:

  ```java
  public FruitFluid getFluid() {
      return FDFluids.JUICE[ordinal()].getSource();
  }
  ```

- `CreateRecipeGen`: fluid **outputs** use `.getSource()`; fluid **inputs** use tag
  ingredients (step 2) so old flowing stacks also match.

  ```java
  b.output(jamFluid.getSource(), 125);
  FluidIngredient.fromTag(FDFluids.sourceTag(jamFluid), 125);
  ...
  b.output(juice.getSource(), 250);
  ...
  FluidIngredient.fromTag(FDFluids.sourceTag(fluid), 1000);
  ```

  If tags are not adopted, inputs can use `FluidIngredient.fromFluid(fluid.getSource(), amount)`;
  that matches new source stacks only.

- Mirror the change on the 1.21 branch, including
  `RegisterCauldronFluidContentEvent`:

  ```java
  event.register(FDCauldrons.JAM[e.ordinal()].get(),
                 FDFluids.JAM[e.ordinal()].getSource(), 1000, null);
  event.register(FDCauldrons.JELLO[e.ordinal()].get(),
                 FDFluids.JELLO[e.ordinal()].getSource(), 1000, null);
  ```

No helper is needed just to avoid repeated `.getSource()` calls; it is cheap and
side-effect free. A helper is still useful for deriving the source id or its tag:

```java
public static TagKey<Fluid> sourceTag(FluidEntry<?> entry) {
    return FluidTags.create(Objects.requireNonNull(
            ForgeRegistries.FLUIDS.getKey(entry.getSource())));
}
```

No change is required in:

- `FruitFluid`
- `FruitFluidType`
- `ClientFruitFluid`
- `VirtualFluidBuilder`
- `JamEffectHandler` (its `instanceof FruitFluid` check matches both source and flowing)

### 2. Add a fluid tag per fluid so both entries match

In `FDFluids`, add one tag per fluid with the source fluid id as the tag id:

```java
FluidTags.create(new ResourceLocation(FruitsDelight.MODID, name + "_jam"))
```

`FluidBuilder#tag(...)` adds that tag to both the flowing entry and the source entry.
Then use `FluidIngredient.fromTag(...)` for all Create fluid ingredients. Details and
caveats are in "Old save compatibility" below.

The same `FluidBuilder#tag(...)` and `FluidIngredient.fromTag(...)` APIs exist in the
1.21 Registrate/Create versions used by Youkais Feasts, so the tag approach ports
directly. Only the generated data-pack folder layout differs between loader versions;
datagen writes the correct path automatically.

### 3. Recipe IDs can move to source-based IDs

`CreateRecipeGen` derives recipe IDs from `FluidEntry#getId()`, which is the flowing
entry ID, for example `fruitsdelight:flowing_apple_jam`, producing
`mixing/flowing_apple_jam.json`.

Changing these IDs is acceptable:

- Recipe IDs are only referenced by the client recipe book. Old IDs silently disappear
  from the book; nothing crashes and no world data becomes unreadable.
- Recipes are datapack data and are reloaded every launch. No block entity, item, or
  entity NBT stores a recipe ID.
- The only loss is that old datapack overrides keyed on `fruitsdelight:flowing_*` stop
  applying. That is acceptable.

Recommended: derive recipe IDs from the source fluid ID.

```java
public static ResourceLocation sourceId(FluidEntry<?> entry) {
    return Objects.requireNonNull(ForgeRegistries.FLUIDS.getKey(entry.getSource()));
}
// 1.21 NeoForge: BuiltInRegistries.FLUID.getKey(entry.getSource())
```

Resulting IDs:

- jam mixing -> `fruitsdelight:apple_jam` -> `mixing/apple_jam.json`
- jello mixing -> `fruitsdelight:apple_jello` -> `mixing/apple_jello.json`
- juice mixing -> `fruitsdelight:orange_juice` -> `mixing/orange_juice.json`

Juice fluid names already carry their type suffix (`_juice`, `_tea`, `_soup`,
`_cocktail`), so all source-derived IDs are descriptive. The `filling/<name>.json`
recipe already uses the same base id in a different recipe-type folder; Create prefixes
the recipe type, so the final ids do not collide
(`fruitsdelight:filling/orange_juice` vs `fruitsdelight:mixing/orange_juice`).

Datagen does not delete stale files. After changing IDs, delete the existing
`src/generated/resources/data/fruitsdelight/recipes/mixing/flowing_*.json` files
(56 of them currently); `runData` writes the new names. All `flowing_*` recipe files
are under `mixing/`.

Expected datagen result after the fluid change alone: no diff in fluid values, because
Create already normalizes passed fluids to source. Recipe names change only if IDs are
changed.

## Old save compatibility

The safe migration strategy is to **keep both registry entries registered**.

- Keep `fruitsdelight:flowing_<name>` registered.
- Keep `fruitsdelight:<name>` registered.
- Do not rename or remove either entry.
- Do not rely on `MissingMappingsEvent` as the primary migration strategy.

This means old NBT referring to:

`fruitsdelight:flowing_apple_jam`

still resolves, so old tanks, items, and block entities load normally.

Old saves will not break. They may still contain flowing stacks after the update, but
those registry IDs remain valid.

The remaining problem is **matching**, not loading: an old stack still holds the
flowing `Fluid` object, and `FluidHelper.isSame` compares fluid identity (`==`). So an
old `fruitsdelight:flowing_apple_jam` stack will not match an ingredient built from
`fruitsdelight:apple_jam`.

Both entries share the same `FruitFluidType`, so old stacks look and behave normally.
Only identity comparisons differ.

### Recommended no-Mixin solution: fluid tags containing both entries

Registrate's `FluidBuilder#tag(TagKey<Fluid>...)` adds the tag to **both** the flowing
entry and its source. It tags itself (the `flowing_<name>` builder entry) and
additionally calls `getSource()` for the source id
(`FluidBuilder.java`, `tag(...)`). One call in `FDFluids` therefore produces a tag
containing both registry ids.

Use the source fluid id as the tag id, mirroring vanilla `minecraft:water` /
`minecraft:flowing_water`:

```json
// data/fruitsdelight/tags/fluids/apple_jam.json
{
  "values": [
    "fruitsdelight:apple_jam",
    "fruitsdelight:flowing_apple_jam"
  ]
}
```

Implementation sketch:

```java
// FDFluids, once per fluid
var tag = FluidTags.create(new ResourceLocation(FruitsDelight.MODID, name + "_jam"));
JAM[e.ordinal()] = virtualFluid(...).tag(tag).register();
```

Generic helper:

```java
public static TagKey<Fluid> sourceTag(FluidEntry<?> entry) {
    return FluidTags.create(Objects.requireNonNull(
            ForgeRegistries.FLUIDS.getKey(entry.getSource())));
}
```

Use it for Create ingredients:

```java
FluidIngredient.fromTag(FDFluids.sourceTag(jamFluid), 125)
FluidIngredient.fromTag(FDFluids.sourceTag(juice), 250)
FluidIngredient.fromTag(FDFluids.sourceTag(fluid), 1000)
```

Why this works (verified against Create 0.5.1 bytecode):

- `FluidIngredient.FluidTagIngredient#testInternal` uses
  `FluidHelper.isTag(stack, tag)` -> `stack.getFluid().is(tag)`. Both source and flowing
  are in the tag, so both pass.
- `determineMatchingFluidStacks()` maps every tag member through
  `FlowingFluid#getSource()` and then `distinct()`. JEI display and network sync
  therefore see a single source stack, not a duplicate pair.
- The recipe JSON ingredient becomes `{"fluidTag": "fruitsdelight:apple_jam"}`
  instead of `{"fluid": "..."}`.

Limits:

- This only helps tag-aware consumers (Create recipe matching, KubeJS, datapacks).
  Code that does `stack.getFluid() == source` still needs a real source stack.
- The tag is ours, not a Forge convention, so unrelated mods will not recognize it
  unless they look it up. `getSource()` at all call sites remains the primary fix.
- Tag ids equal to the source fluid id are canonical and descriptive
  (`fruitsdelight:apple_jam`, `fruitsdelight:orange_juice`, ...). Item/fluid/block tags
  live in separate registries, so there is no collision with items.

### Why not registry aliases?

Forge 1.20.1 `ForgeRegistry#getValue` resolves aliases, and
`FluidStack.loadFluidStackFromNBT` uses `getValue`, so an alias mapping
`flowing_x -> x` would convert old stacks on load without a Mixin. However:

- `ForgeRegistry#addAlias` is not public API in Forge 47.4.10. `IForgeRegistry` does not
  expose it, and `RegistryBuilder` has no alias method (there is a TODO in Forge to make
  it public). Using it requires casting to the internal class.
- Aliases are only consulted when the requested id is missing:

  ```java
  V ret = this.names.get(key);
  key = this.aliases.get(key);
  while (ret == null && key != null) { ... }
  ```

  Since `flowing_*` stays registered, the alias is never used.
- Therefore alias-based normalization requires removing the `flowing_*` registrations
  and remapping them through `MissingMappingsEvent`, which is the risky path below.
- NeoForge 1.21 (Youkais Feasts target) has no Forge registry aliases and no
  `MissingMappingsEvent` at all, so the approach does not port.

Conclusion: aliases are not a viable no-Mixin option while both entries stay registered.

### Last resort: Mixin deserialization migration

Only needed if old flowing stacks must satisfy strict identity checks in code we do not
control and that has no tag-based path. It is **not** needed for world loading, and tags
cover our own recipes.

Possible targets in Forge:

- `FluidStack.loadFluidStackFromNBT(CompoundTag)`
- `FluidStack.readFromPacket(FriendlyByteBuf)`

For any fluid stack in the `fruitsdelight` namespace whose path starts with
`flowing_`:

1. Remove the `flowing_` prefix to find the source fluid ID.
2. Replace the stack's fluid with the source fluid.
3. Let normal loading continue.

This covers saved block entities, item NBT, entity data, and network synchronization.
The project already has Mixin and MixinExtras available; `PlayerMixin` already uses
`@ModifyReturnValue`. A new mixin must be added to
`src/main/resources/fruitsdelight.mixins.json`.

### What not to do

Do **not** remove the flowing fluid registrations and remap them through
`MissingMappingsEvent`.

Risks:

- Registrate's `FluidBuilder`/`FluidEntry` are built around the flowing entry
  (`get()`, `getId()`, `getType()`, `getBlock()`), so removing it requires bypassing
  Registrate internals.
- Old datapack tags naming `fruitsdelight:flowing_*` stop resolving: tag loading uses
  holder lookups (`holdersByName`), which do not consult registry aliases.
- Other mods may hardcode or compare the flowing id/key.
- 1.21/NeoForge has no equivalent remapping event, so the 1.20 solution would not port.
- Keeping both ids registered is much safer; the tag approach solves matching.

## Validation checklist

- Run `./gradlew runData`.
  - Confirm new `data/fruitsdelight/tags/fluids/*.json` files contain both the source
    and `flowing_` ids.
  - Confirm Create recipe ingredients use `fluidTag` where tags are used, and outputs
    still use source fluid ids.
  - Confirm recipe IDs changed as intended and delete stale `mixing/flowing_*.json`.
- Run `./gradlew build`.
- Test a new world:
  - Create mixing, filling, emptying, and compacting recipes.
  - JEI/REI fluid display (tag ingredients should show one fluid, not two).
  - Cauldron interactions (1.21).
- Test an old save:
  - Load a world containing both source and flowing fluid stacks.
  - Confirm the world loads without missing fluid errors.
  - Confirm Create recipes accept both old flowing stacks and new source stacks via the
    tag ingredients.
  - If the optional Mixin is implemented, confirm old flowing stacks are converted to
    source on load.

## Summary

1. Keep Registrate registration exactly as-is; both ids stay registered.
2. Replace every consumer-side `FluidEntry#get()` with `FluidEntry#getSource()`.
3. Add a fluid tag per fluid (id = source fluid id) via `FluidBuilder#tag`, so both
   source and flowing ids are recognized by tag-aware matching.
4. Use `FluidIngredient.fromTag(...)` in `CreateRecipeGen` so old flowing stacks match.
5. Move recipe IDs to source-based ids; old recipe-book entries disappear harmlessly.
6. A `FluidStack` Mixin migration is optional and only for strict identity checks in
   third-party code.
